# Knowledge Record

当用户要求记录问答时，将知识记录到当前工作目录的 `.md` 文件中。

## 工作流程

### 1. 确定文件名

从用户的问题中提取核心主题，生成简洁的英文文件名（kebab-case），例如：
- 关于 Python async/await → `python-async-await.md`
- Docker 网络配置问题 → `docker-network-config.md`

规则：
- 使用小写字母、数字和连字符
- 长度控制在 3-8 个单词
- 文件名要有辨识度，能概括问题主题

### 2. 检查命名冲突

用 Glob 工具检查 CWD 中是否已存在同名文件：
- 如果不存在 → 直接创建
- 如果存在且是同一会话中创建的 → 追加内容
- 如果存在但不是同一会话的 → 添加数字后缀（`-1`, `-2`...）

> 同一会话内：记住本次会话中创建/追加过的文件名，后续追加提问使用同一个文件。

### 3. 内容结构

每条记录包含以下部分（按实际情况裁剪）：

#### 首次记录格式

```markdown
# <主题英文标题>

---

begin modify by knowledge_record at <yyyy-MM-dd hh:mm>

## 问题: <问题的概括性描述，不超过20字>

<用户的问题>

## 解答

<你的解答>

### 相关知识

- <相关知识点 1>
- <相关知识点 2>

### 与其他知识的联系

- <与其他领域的联系>
- <与已知概念的对比>

### 潜在问题与注意事项

- <注意事项 1>
- <边界情况>

end modify by knowledge_record at <yyyy-MM-dd hh:mm>

---
```

#### 追加提问格式

在已有文件末尾追加新块：

```markdown
---

begin modify by knowledge_record at <yyyy-MM-dd hh:mm>

## 追加问题: <追加问题的概括性描述，不超过20字>

<用户的追问>

## 追加解答

<你的解答>

### 方案变更（如果有）

**原方案**: <之前推荐的方案>
**问题**: <方案存在的问题>
**新方案**: <调整后的方案>
**问题原因**: <为什么原方案有问题>

### 追加相关知识

- <新知识点>

end modify by knowledge_record at <yyyy-MM-dd hh:mm>

---
```

### 4. 方案变更处理

当用户说方案有问题、需要换方案时，**重点记录**：

1. **原方案**是什么
2. **问题/报错**是什么
3. **问题原因**（关键！用户特别强调要记录原因）
4. **新方案**是什么
5. 新的相关知识

将"方案变更"块放在追加回答中，确保问题原因清晰可见。

### 5. 会话管理

- 同一会话内，首次创建文件后记住文件名，后续追加提问直接使用同一文件
- 如果用户开启了一个全新的主题（与之前记录的主题无关），创建新文件
- 如果无法确定是否是同一主题，询问用户

## 注意事项

- 不要修改用户在之前条目中已确认的内容，除非用户要求修改
- 不要重复记录完全相同的内容
- 知识记录文件仅供记录，不影响你对当前问题的正常回答
